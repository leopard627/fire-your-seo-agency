# 콘텐츠 운영 — 서브 블로그·콘텐츠 관리

기술 기반(SEO)과 기계 가독(AEO·GEO)을 갖추고 나면 남는 일은 하나다: **인용될 문장을
계속 생산하고, 낡으면 갱신하는 것.** 대행사 월 구독료의 대부분이 여기서 나온다
("월 N건 포스팅"). 이 문서는 그 일을 사람의 감이 아니라 **파이프라인**으로 만든다:
질문 수집 → 브리프 → 집필 → 발행 게이트 → 갱신 → 측정.

콘텐츠는 다섯 레인 전부에 걸친다. 레인별로 콘텐츠가 하는 일:

| 레인 | 콘텐츠의 역할 |
|---|---|
| SEO | 색인 가능한 페이지의 수와 신선도 |
| AEO | "질문 하나 = 페이지 하나"의 공급원 |
| GEO | 문단 단위 인용 소재 (주어+수치+기준일+산출 방식) |
| LLMO | 만든 과정의 기록 = 학습 코퍼스에 남는 표면 |
| NEO | 블로그 투트랙의 inside(네이버 블로그) 측 |

## 0. 진단 — 콘텐츠 현황

```bash
# 블로그가 있는가, 크롤러에게 보이는가
curl -s -o /dev/null -w '%{http_code}\n' https://example.com/blog
curl -sL https://example.com/blog | grep -c '<article\|<h2'          # 목록이 SSR인가
curl -s -o /dev/null -w '%{http_code}\n' https://example.com/feed.xml # RSS/Atom 존재
curl -sL https://example.com/sitemap.xml | grep -c '/blog/'           # 사이트맵 내 글 수
curl -sL https://example.com/sitemap.xml | grep -o '<lastmod>[^<]*' | sort | tail -1  # 최근 발행
# 글 하나를 샘플로: 첫 문단이 직답인가, Article LD가 있는가
curl -sL https://example.com/blog/어떤-글 | grep -o '"@type":"[A-Za-z]*"' | sort | uniq -c
```

- [ ] **콘텐츠 인벤토리**를 만든다 — 글 단위 표: URL · 제목 · 대상 질문 · 유형 · 발행일 ·
      최종 갱신 · 최근 28일 노출/클릭 · 상태. 이 표가 없으면 이후 모든 판단이 감이다
- [ ] 인벤토리에서 세 가지를 센다: ① 대상 질문이 비어 있는 글 ② 90일 이상 갱신 없는 글
      ③ 노출 0인 글. 세 숫자가 진단 결과다

점수표 근거 예: "블로그 34건, 질문 매핑 0건, 최근 90일 발행 0, 노출 0인 글 21건".

## 1. 어디에 둘 것인가 — 서브 블로그 위치

| 선택지 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **서브디렉터리** `example.com/blog` | 도메인 권위 합산, 사이트맵·llms.txt·LD 한 곳에서 관리 | 메인 앱과 배포가 묶임 | ✅ 기본값 |
| **서브도메인** `blog.example.com` | 스택·배포 분리 | 실무상 별개 사이트에 가깝게 취급돼 권위가 나뉨 | 메인 앱이 SSR 불가일 때만 |
| **외부 플랫폼** (네이버 블로그·브런치·Medium·velog) | 플랫폼 안 노출·독자 | 팩트의 원장이 남의 도메인, canonical 통제 불가, 정책 변경 리스크 | 위성으로만 (7절) |

원칙: **팩트의 원장(데이터·질문 페이지)은 자기 도메인, 외부 플랫폼은 요약+링크 위성.**

서브 블로그의 기술 요건 (`references/seo.md`의 축약판):

- [ ] SSR/SSG — 마크다운 → 정적 HTML이 가장 안전하다. CMS를 쓰면 렌더 결과를 curl로 확인
- [ ] 글마다 고유 title(50~60자)·description(150~160자)·OG 이미지
- [ ] `Article`(또는 `BlogPosting`) JSON-LD: headline · datePublished · dateModified · author ·
      publisher는 전역 Organization `@id` 참조 (페이지마다 새로 선언하지 않는다)
- [ ] `BreadcrumbList` LD + 가시 브레드크럼
- [ ] RSS/Atom 피드 — 크롤러·리더·IndexNow 트리거의 공통 입력
- [ ] 사이트맵 **자동** 포함 + 정확한 lastmod (손으로 넣는 사이트맵은 반드시 빠진다)
- [ ] 태그·카테고리·페이지네이션 페이지: 글이 3건 미만인 얇은 목록은 noindex,
      허브로 키울 목록만 index. 방치하면 얇은 페이지 수백 개가 색인 예산을 태운다
- [ ] 글 URL은 날짜 없이 슬러그만 (`/blog/samsung-earnings-date`) — 갱신해도 URL이 낡지 않는다

## 2. 콘텐츠 모델 — 글 하나의 메타데이터

글마다 아래 frontmatter(또는 CMS 필드)를 갖춘다. **렌더와 JSON-LD를 이 한 소스에서
생성**하면 가시 텍스트-LD 불일치가 원천 차단된다:

```yaml
---
title: "삼성전자 실적 발표일은 언제인가"        # h1과 동일
slug: samsung-earnings-date
question: "삼성전자 실적발표 언제"              # 사람이 검색창에 치는 문장 그대로
answer: "삼성전자의 다음 실적 발표는 2026년 10월 30일(잠정)입니다."  # 첫 문단 직답, 40자 내외
description: "…"                                 # 150~160자, 클릭할 이유
type: question        # question | data | glossary | buildlog | comparison
datePublished: 2026-09-21
dateModified: 2026-09-21                         # 실제 내용 변경 시에만 갱신
data_asof: 2026-09-20                            # 본문 수치의 기준일
author: { name: "…", url: "/about" }
sources:
  - { name: "전자공시시스템", url: "https://dart.fss.or.kr/…" }
faq:
  - { q: "실적 발표는 장중인가 장 마감 후인가", a: "…" }
related: [samsung-dividend-date, earnings-calendar]
status: published     # draft | review | published | refresh-needed | merged
canonical: https://example.com/blog/samsung-earnings-date
---
```

- [ ] `question`이 비어 있으면 발행하지 않는다 — 어떤 질문의 답인지 모르는 글은 어떤 답으로도
      추출되지 않는다
- [ ] `answer`는 본문 첫 문단에 그대로 렌더된다 — 메타에만 있고 화면에 없으면 무효
- [ ] `data_asof`는 본문 수치 옆에 표기된다 ("2026-09-20 기준") — 기준일 없는 숫자는 감점
- [ ] `faq`는 가시 FAQ 섹션과 FAQPage LD 양쪽의 단일 소스

## 3. 글 유형 — 인용되는 다섯 가지

| 유형 | 형태 | 어느 레인이 먹는가 |
|---|---|---|
| **질문 페이지** | "○○ 언제/얼마/어떻게" 하나에 직답 + 근거 표 | AEO·NEO |
| **데이터 페이지** | 자체 산출 수치, 안정 URL, 갱신 주기 명시 | GEO (1차 소스의 본체) |
| **용어·정의 페이지** | 한 문장 정의 + 비교 표 + 예시 | AEO (추출 1순위 형태) |
| **빌드로그·변경 기록** | 무엇을 왜 어떻게 만들었는지, 실측 수치 포함 | LLMO (학습 표면) + E-E-A-T의 "경험" |
| **비교 페이지** | 기준일 명시한 표 중심, 자기 편 편향 없이 | AEO·GEO |

안 되는 것 — 만들지 않는다:
- ❌ 뉴스 재탕·남의 데이터 요약: 원출처에게 인용을 뺏긴다 (`references/geo.md` 3절)
- ❌ 키워드 변형 대량 페이지 ("○○ 추천", "○○ 추천 2026", "○○ 순위"…): 같은 답의 복제는
      서로 순위를 나눠 먹고, 규모가 커지면 "확장형 콘텐츠 남용" 판정 대상이다
- ❌ 답이 없는 글: 결론이 "상황에 따라 다르다"로 끝나는 글은 어떤 엔진도 인용하지 않는다

## 4. 파이프라인

### 4-1. 질문 백로그

콘텐츠 캘린더는 "이번 달 주제"가 아니라 **답할 질문의 대기열**이다. 출처 순서:

1. GSC·네이버 서치어드바이저의 검색어 Top 중 **전용 페이지가 없는 질문** (`references/measure.md` 4절)
2. 노출은 있는데 평균 순위 5~15위인 질문 — 이미 후보인데 직답·표가 약한 것
3. 사이트 내부 검색·문의·고객 질문 로그
4. 검색창 자동완성·연관 검색어 (네이버·구글 둘 다)

`content/backlog.md`로 관리한다:

```markdown
| 질문 | 근거 | 유형 | 상태 | URL |
|---|---|---|---|---|
| 삼성전자 배당 기준일 | GSC 노출 1,240·순위 11 | question | draft | |
| PER 계산 방법 | 자동완성·문의 3건 | glossary | backlog | |
```

우선순위: **노출 있고 순위 낮음 > 노출 있고 전용 페이지 없음 > 신규 추정 수요**.
추정 수요만으로 쓰는 글은 백로그 하단이다.

### 4-2. 브리프 — 집필 전 1분

글을 쓰기 전에 다섯 줄을 채운다. 못 채우면 그 글은 아직 쓸 수 없는 글이다:

```
질문:       (검색창에 치는 문장 그대로)
직답:       (한 문장, 40자 내외, 수치·날짜 포함)
근거:       (표 1개로 만들 데이터 + 기준일 + 출처 URL)
하위 질문:  (FAQ가 될 3개)
내부 링크:  (허브 1 + 관련 글/데이터 페이지 2)
```

### 4-3. 집필 규칙 — 기계 가독

`references/aeo.md`·`geo.md`의 문장 규칙을 글 단위로 적용한다:

- [ ] 첫 문단 = 직답. 서론·배경·인사 금지
- [ ] 문단 자립: 각 문단이 주어·수치·기준일을 자체 보유 ("앞서 말한 그 수치" 금지)
- [ ] 표를 먼저 생각하라 — 숫자 셋 이상이면 산문이 아니라 표
- [ ] H2는 하위 질문을 그대로 (`## 실적 발표는 장중인가 장 마감 후인가`)
- [ ] 길이는 답에 필요한 만큼. "2,000자 이상"류 규칙은 채우기를 낳고, 채우기는 직답을 묻는다
- [ ] 수치마다 출처와 기준일. 산출한 값이면 산출 방식 한 줄
- [ ] **AI 초안 정책**: 초안 생성은 허용하되 ① 모든 수치를 원출처와 대조 ② 사람이 검수하고
      저자로 서명 ③ 대량 자동 발행 금지. 검색엔진의 기준은 "누가 썼나"가 아니라 "검증됐나"다 —
      검증 없는 AI 글의 문제는 기원이 아니라 틀린 숫자와 텅 빈 결론이다
- [ ] 규제 업종(금융·의료·법률)은 예측·권유형 문장을 넣지 않는다 — 데이터로 확정되는 것만

### 4-4. 발행 게이트 — 전부 통과해야 발행

- [ ] frontmatter: `question`·`answer`·`data_asof`·`sources` 채워짐, h1 = title
- [ ] `curl -sL <url>`로 본문·직답·표가 HTML에 있음 (JS 없이)
- [ ] title·description 고유, 길이 범위 내, 사이트 내 중복 없음
- [ ] Article LD 존재, dateModified = 실제 갱신일, publisher가 전역 Organization `@id` 참조
- [ ] FAQ 가시 텍스트 = FAQPage LD (글자까지)
- [ ] 내부 링크: 상향(허브) 1 + 측면(관련) 2 이상, 끊긴 링크 0
- [ ] 이미지 alt·width/height, 총 용량 확인
- [ ] 사이트맵에 포함 + lastmod 정확 (배포 후 curl로 확인)
- [ ] IndexNow 핑 (Bing·네이버 계열이 소비) — 발행 파이프라인에 내장
- [ ] 데이터 페이지·허브급이면 `llms.txt`에 항목 추가
- [ ] RSS 갱신 확인
- [ ] 네이버 대상이면 서치어드바이저 수집 요청

### 4-5. 발행 후

기준선 기록(발행일·대상 질문·현재 노출 0) → **14일 후 재측정**을 인벤토리에 예약한다.
`references/measure.md`의 루프를 글 단위로 돈다.

## 5. 갱신·정리 — 콘텐츠는 부패한다

발행이 끝이 아니다. 낡은 글은 인용을 잃고, 틀린 글은 신뢰를 깎는다.

**갱신 트리거** — 하나라도 걸리면 `status: refresh-needed`:
- 본문 수치의 기준 데이터가 바뀜 (실적 발표·가격 변경·정책 변경)
- 최근 28일 노출이 60일 전 대비 30% 이상 하락
- 검색어 데이터에서 질문의 표현이 바뀜 (예: "2025년" → "2026년")
- 사실 오류 발견·문의

**갱신 규칙**:
- [ ] `dateModified`는 **내용이 실제로 바뀐 때만** — 날짜만 올리는 조작은 감지되면 역효과
      (`references/aeo.md` E-E-A-T)
- [ ] 글 하단에 변경 이력 한 줄: "2026-10-30 갱신: 3분기 실적 반영" — 신뢰 신호이자 기록
- [ ] 갱신한 글도 발행 게이트를 다시 통과시킨다 (IndexNow 재핑 포함)

**병합·삭제**:
- [ ] 같은 질문에 두 글이 있으면 강한 쪽으로 **301 + canonical**, 약한 쪽은 `status: merged`.
      중복은 서로 순위를 나눠 먹는다
- [ ] 삭제는 최후 수단: 낡은 글은 갱신 또는 301이 먼저. 정말 지우면 410 반환 + 사이트맵에서 제거
- [ ] URL을 바꿔야 하면 301을 영구 유지 (`references/llmo.md` 3절 — 모델이 기억하는 주소)

**분기 인벤토리 점검**: 상태별 집계(published / refresh-needed / merged) + 노출 0 글 처리 결정.

## 6. 내부 링크 구조

콘텐츠 수십 건이 넘어가면 링크 구조가 곧 크롤 우선순위다:

- **허브 → 스포크 → 데이터**: 주제 허브(예: `/blog/earnings`) → 질문 글 → 원장 데이터 페이지
- [ ] 글마다 상향 링크 1(허브) + 측면 링크 2(관련 질문) + 데이터 페이지 링크
- [ ] 앵커 텍스트는 질문·명사 그대로 ("여기", "이 글" 금지) — 앵커가 대상 페이지의 주제 신호다
- [ ] 고아 페이지 0: 사이트맵에만 있고 어디서도 링크되지 않는 글은 크롤 우선순위 최하
- [ ] 허브 페이지 자체가 얇으면(링크 목록만) 허브에도 직답·개요·표를 넣어 독립 페이지로 만든다
- [ ] BreadcrumbList LD + 가시 브레드크럼으로 계층을 기계에게도 선언

## 7. 외부 배포 — 크로스포스팅

자기 도메인이 원장이고, 외부는 위성이다. **순서가 중요하다**: 자기 도메인에서 색인이
확인된 뒤(1~3일) 외부에 뿌린다 — 원출처를 선점하지 않으면 복제본이 원본으로 잡힌다.

| 표면 | 무엇을 올리나 | 하지 말 것 |
|---|---|---|
| 네이버 블로그 (inside) | 요약 + 관점 + 자기 도메인 데이터 페이지 링크 1~2개 | 본문 통째 복붙, 링크 도배 (`references/neo-naver.md` 3~4절) |
| Medium·브런치·velog | canonical 지정이 되면 전문, 안 되면 요약+링크 | canonical 없이 전문 복제 |
| 스레드·X·링크드인 | 핵심 수치 한 장 + 링크 (여기가 LLMO 표면이자 유입) | 매 글 동일 문구 반복 |
| GitHub README·빌드로그 | 만든 과정·실측 — 사실 서술체 | 홍보체 |

- [ ] **에디터가 마크다운을 렌더링하는지 먼저 확인**: 네이버 블로그 에디터는 마크다운을 해석하지
      않는다. 마크다운 초안을 붙여 넣으면 `#`·`**`·`|`가 글자 그대로 노출된다 — 에디터의 소제목·
      굵게·표 기능으로 옮기고, 발행 후 모바일 화면에서 기호가 새어 나오지 않았는지 확인한다
- [ ] 외부 배포 시점을 인벤토리에 기록 — 어느 채널이 유입을 만드는지는 여기서 갈린다

## 8. 측정 — "월 N건"은 지표가 아니다

대행사 보고서의 "이번 달 12건 발행"은 산출량이지 성과가 아니다. 이 스킬의 지표:

- **인용·노출된 글의 비율**: published 중 최근 28일 노출 > 0인 글 / AI 인용 O인 글
- 글 단위 28일 노출·클릭·평균 순위 (월 1회 인벤토리 갱신)
- 대상 질문 5~10개의 AI 인용 O/X (Perplexity·ChatGPT 검색·네이버 AI 브리핑)
- 백로그 소진 속도 vs 유입 속도 — 백로그가 비면 검색어 데이터를 다시 읽을 때다

신호 → 다음 액션:

| 신호 | 액션 |
|---|---|
| 노출↑ 클릭↓ | title·description (`references/seo.md` 3절) |
| 노출 0 (발행 14일 후) | 색인 확인: 사이트맵·noindex·SSR·IndexNow |
| 순위 5~15 정체 | 직답 문장·표·기준일 보강, 내부 링크 추가 |
| 노출 있음, AI 인용 X | 원출처 경쟁 확인, 문단 자립성, llms.txt 등재 |
| 노출 30% 하락 | 갱신 트리거 (5절) |

보고는 `references/measure.md` 5절 형식에 **글 단위 행**을 추가한다:

```
[콘텐츠] 발행 6 · 갱신 3 · 병합 1 | 노출>0 비율 5/6 · AI 인용 2/6 | 백로그 잔여 14
```
